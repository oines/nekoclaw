# Nekoclaw 人物沉淀 Harness（v5）

## 目标

用可自动化回放的方式验证 nekoclaw 的 v5 人物沉淀系统是否满足分层记忆、旁观采集、按需读正文、异步 formation、Dream 全局整理和自然老化的行为要求。

全部场景都由 harness 模拟消息流，收集 bot 最终回复，再交给 LLM judge 判定 `pass / fail + 原因`。

## 场景列表

### 场景 1：群聊旁观
- 群里没有触发 bot 时，先累积 observations。
- 后续有人询问“刚才在聊什么”时，bot 应该基于近期旁观记录概括。
- 不能把旁观说成参与，不能编造证据里不存在的细节。

### 场景 2：跨 session 记忆
- 同一账号在新的私聊轮次中追问“上次聊的项目还记得吗”。
- bot 应该回忆起之前的项目背景，而不是只依赖当前 session。

### 场景 3：记住“不像属性”的记忆
- 通过多轮私聊沉淀压力、导师改方向、deadline 摸鱼等自由文本背景。
- 用户只说“唉又来了”时，bot 应能接住处境，而不是当成全新话题。

### 场景 4：跨平台自然语言认人
- TG 上认识的人在 NapCat/QQ 上自称“我是之前 TG 上那个小王”。
- bot 应该自然关联；不确定时允许先确认，但不能装作完全确定。

### 场景 5：自然语言纠偏
- 新用户以“我是小王同事”进入，再自报“我叫李四”，之后发生“你认错了我不是小王”纠偏。
- 当前和后续 session 都不能继续把李四当成小王。

### 场景 6：经历沉淀与跨时间关联
- 同一人在群里先和 bot 讨论 Python 异步、数据库选型，之后 bot 旁观到“数据库果然不行要换”。
- 后续私聊回忆时，bot 需要把这些经历串起来，并区分参与和旁观。

### 场景 7：不确定时表达不确定
- 群里同时有“老王”和“王老师”，新私聊账号自称“我是群里的老王”。
- bot 如果证据不足，应主动确认，不允许静默猜测。

### 场景 8：多群同一人经历整合
- 同一人在群 A 和群 B 分别留下 bot 参与过的经历和 bot 旁观到的经历。
- 后续私聊时，bot 需要整合两个群的内容，并保持来源清晰。

### 场景 9：记忆自然老化
- 通过预填 persona Markdown 文件模拟“一个月前的临时琐事”和“长期重要背景”并存。
- 无关语境下，bot 不应主动提起过期琐事；长期背景仍应保留。

### 场景 10：Dream 跨场景人物关联
- 预填多个 scene 文件，分别记录同一人在不同群里的经历。
- 触发 Dream 后，people 文件和 index 摘要应体现跨场景整合结果。

### 场景 11：Dream 全局重整 index
- 预填重复、过时、失效引用的 index.md。
- Dream 后 index 应与现有 memory 文件一致，并消除重复和陈旧摘要。

### 场景 12：Dream 全局老化
- 预填长期不活跃人物与持续活跃人物的长篇 people 文件。
- Dream 应压缩不活跃人物、保留核心信息，并避免同等力度压缩活跃人物。

### 场景 13：Dream 发现 formation 遗漏
- 预填多个 scene 文件反复提及同一人，但不存在 people 文件。
- Dream 应基于多处提及创建新的 people 文件和 index 条目，且不得编造背景。

### 场景 14：Dream 不破坏纠偏与跨平台关联
- 预填纠偏信息和跨平台身份关联。
- Dream 后再跑正常对话，bot 不应出现认错人或丢失跨平台关联的回退。

## 约束

### 结构约束
1. 不通过给 `message-router.ts` 继续加 persona 特判分支来实现能力。
2. worker 不直接读取 `.nekoclaw-persona/` 原始目录；worker 只消费预组装的人物上下文文本层。
3. observation 采集、selector、formation、prompt 拼装要可独立测试。

### 行为约束
1. 当前 session 信息优先级最高。
2. 旁观不能说成参与。
3. 不确定不能说成确定。
4. 纠偏必须持久化。
5. 记忆内容不受 schema 限制，保持 Markdown 自然语言。

### 技术约束
1. 只使用文件型存储，不引入数据库或向量服务。
2. v1 覆盖 Telegram 和 NapCat。
3. 不改变现有 `sessionKey` 模型。

## 验收方式

每个 persona harness 场景都遵循同一个闭环：

1. 模拟对应平台的消息输入序列。
2. 收集 bot 最终回复。
3. 将预期、失败信号、最终回复和相关证据交给 LLM judge。
4. judge 返回 `pass` 或 `fail` 以及原因。

所有 persona + Dream 场景都通过，才算当前人物沉淀系统验收通过。
